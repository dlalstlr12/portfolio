01 · 예약 동시성 — 오버부킹

문제

락 없이 조회 → 검증 → 저장 순서로 예약을 만들면, 같은 룸·겹치는 시간에 예약이 여러 건 생기는 오버부킹이 발생합니다. 이론으로 아는 상태로 두지 않고 k6로 20 VU를 동시에 태워 실제로 재현했습니다. (check-then-act 레이스)

접근

reservation.lock.strategy 설정 하나로 락 없음 → DB 비관적 락 → Redisson 분산 락을 전환할 수 있게 만들고, 동일한 시나리오·동일한 부하로 세 번 측정했습니다.

결과

전략오버부킹처리량p95
락 없음10건 (버그)761 req/s49 ms
비관적 락 (최종 채택)1건334 req/s83 ms
Redisson 분산 락1건127 req/s205 ms

판단

비관적 락은 정합성을 얻는 대신 처리량 −56%, 분산 락은 단일 핫키 기준 −83% (Redis 왕복 2회)입니다. 다만 분산 락은 앱을 여러 대로 늘렸을 때 DB 락 경합이 사라지므로, 현재 배포 형태가 단일 인스턴스라는 이유로 기본값을 비관적 락으로 두고 분산 락은 선택 가능하게 남겼습니다.

낙관적 락도 검토했지만, 이 경우는 INSERT vs INSERT라 충돌을 감지할 기존 행 자체가 없어 @Version으로는 막을 수 없다는 것을 확인하고 채택하지 않았습니다.

02 · 알림 — 비동기 · 재시도 · DLT

문제

전체 공지를 동기로 발송하면 API 응답이 회원 수만큼의 발송을 전부 기다립니다. 발송처 한 곳이 느려지면 공지 API 전체가 함께 느려집니다.

접근

@TransactionalEventListener(AFTER_COMMIT)으로 커밋 이후에만 Kafka에 발행하고, 실제 발송은 워커가 소비합니다. 발송 실패는 @RetryableTopic 지수 백오프(0.5s → 1s → 2s)로 재시도하고, 소진되면 DLT로 격리해 정상 트래픽을 막지 않게 했습니다. Kafka는 at-least-once이므로 dedup_key UNIQUE 제약으로 재처리 시 알림이 중복 저장되지 않도록 멱등을 보장했습니다.

결과

  • 공지 발행 p95 ~27 ms — 팬아웃 규모와 무관해졌습니다
  • 발송 장애율 0.3을 인위로 주입했을 때 최종 실패율 0.79% — 이론값 0.3⁴ ≈ 0.81%(원본 1회 + 재시도 3회)와 일치해 재시도 체인이 의도대로 동작함을 확인했습니다

03 · 정기결제 — Spring Batch · 아웃박스 · 멱등

문제

결제 성공 → 이벤트 발행 사이에 브로커가 죽으면 돈은 빠져나갔는데 후속 처리(알림 · 상태 반영)는 사라집니다. 반대로 배치가 재실행되면 같은 주기에 이중 결제가 날 수 있습니다.

접근

  • 유실 방지 — payments 저장 + subscription 상태 변경 + outbox_events 저장을 한 트랜잭션으로 묶고, 별도 릴레이가 미발행 행을 FOR UPDATE SKIP LOCKED로 읽어 Kafka에 발행합니다. 브로커가 죽어 있어도 행은 DB에 남아 다음 폴링에서 재발행됩니다
  • 중복 방지 — 결제 요청에 idempotency_key(sub:{id}:{yyyy-MM})를 부여하고 UNIQUE 제약을 걸었습니다
  • 부분 실패 격리 — 배치 한 건의 실패가 잡 전체를 롤백하지 않도록 건별 REQUIRES_NEW + faultTolerant().skip()으로 처리했습니다

결과

  • 8스레드가 같은 결제 주기를 동시에 호출해도 결제는 정확히 1건
  • 배치 50건 처리 ~1.1s, 아웃박스 드레인 < 4s
  • 실패한 건만 PAST_DUE로 남고 나머지는 정상 커밋
